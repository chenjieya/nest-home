## 1. 访问链路

```text
浏览器 https://nest.alvis.org.cn
  → 宿主机 Nginx :443（证书仍由宿主机管理）
  → 127.0.0.1:8000 → app:12445
      ├─ 页面、图片：由 Nest 静态服务返回
      └─ /api/weather：转发到 weather:3001
                             ├─ 高德 IP 定位、天气
                             └─ 原备用天气接口（校验目标城市）
```

一个仓库产出两个独立镜像：`ghcr.io/chenjieya/nest-home` 和 `ghcr.io/chenjieya/nest-weather`。天气服务只使用 Node 22 内置模块，没有新增 npm 依赖。主 Compose 不向宿主机发布天气端口；浏览器同源调用，无需 CORS。

现有 Nest 反代入口保持 8000，但处理该站点请求的 Nginx `location` 必须包含下面的真实 IP 设置：

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

`TRUST_PROXY=true` 只适用于这一受控链路，不能把容器端口直接暴露公网并信任任意客户端的头。若前面还有 CDN，应先由 Nginx 按可信 CDN 网段正确恢复来源地址。未恢复真实 IP 时，可能定位到 CDN 或返回不可用。

## 2. 服务器首次配置

默认部署目录为 `/home/alvis/nest-home`。在服务器执行以下命令创建私有配置；如果改了仓库变量 `DEPLOY_DIR`，相应修改目录。已有文件不要覆盖。

```bash
mkdir -p /home/alvis/nest-home
cd /home/alvis/nest-home
touch .env.weather
chmod 600 .env.weather
nano .env.weather
```

最小配置如下，在编辑器中填入自己的值，不要把真实 Key 写进终端命令历史：

```dotenv
AMAP_KEY=填写自己的高德Web服务Key
AMAP_MONTHLY_LIMIT=4000
```

完整可选项在 `services/weather/.env.example`。该模板全部为公开默认值，CI 可上传模板，但不会上传或覆盖 `.env.weather`。环境变量在服务器启动容器时注入，不会因为进入容器环境而自动进入 Git。`.gitignore` 和两个 Docker 构建上下文也排除了真实配置。

高德使用 Web 服务类型 Key；如果开启 IP 白名单，应填写服务器实际公网出口 IPv4。访问者 IP 由后端通过定位接口的 `ip` 参数传递，不能用服务器自身位置代替访客。不要再在前端设置 `VITE_WEATHER_KEY`，本次代码不再读取它。

配置在容器运行时仍可被有 Docker 管理权限的人查看。如需用文件注入，可设置 `AMAP_KEY_FILE=/run/secrets/amap_key`，并把服务器密钥文件只读挂载到该路径；确保容器内 node 用户有读取权限。普通部署使用 `.env.weather` 即可。

## 3. CI 与后续更新

GitHub 仓库 Secrets 保留 `SSH_HOST`、`SSH_USER`、`SSH_PASS`，可选 `SSH_PORT`。天气 Key 不需要配置为 GitHub Secret 或 Variable。可选仓库变量 `DEPLOY_DIR` 用于覆盖默认目录。

推送 `main` 后依次执行：天气测试 → 构建两个镜像 → 上传 Compose 和公开模板 → 检查服务器 `.env.weather` → 拉取该提交对应的两个镜像 → 等待容器健康 → 检查主页和天气代理存活接口。

缺少 `.env.weather` 会在更新容器之前报错；先创建文件，再重新运行部署 job。未配置 SSH Secrets 时只构建镜像并提示跳过部署。健康检查不调用第三方，不验证 Key 是否有效，真实天气需另行验证。

以后改天气 Key 或服务配置，在服务器编辑 `.env.weather`，然后执行：

```bash
cd /home/alvis/nest-home
docker compose --env-file .deploy.env up -d --no-build --force-recreate weather
```

无需重新构建镜像；仅 `docker compose restart` 不会重新注入修改后的环境变量。`.deploy.env` 是 CI 保存的两个镜像版本，首次成功部署后生成，不含 Key。

## 4. 缓存、备用与调用上限

| 配置 | 默认值 | 作用 |
| :-- | :-- | :-- |
| CACHE_TTL_SECONDS | 600 | 城市天气缓存 10 分钟，同一城市复用 |
| STALE_TTL_SECONDS | 3600 | 缓存到期后，上游失败最多再展示 1 小时，页面标注缓存 |
| CACHE_MAX_ENTRIES | 1000 | 每类内存缓存最多保存条目数 |
| UPSTREAM_TIMEOUT_MS | 4000 | 每个上游请求的超时 |
| RATE_LIMIT_PER_MINUTE | 20 | 每个来源 IP 的分钟请求上限 |
| GLOBAL_RATE_LIMIT_PER_MINUTE | 120 | 整个实例的分钟请求上限 |
| AMAP_MONTHLY_LIMIT | 4000 | 高德定位和天气请求尝试合并计数；0 禁止调用 |
| FALLBACK_ENABLED | true | 是否尝试原备用天气服务 |
| FALLBACK_WEATHER_URL | 模板中的 oioweb 地址 | 服务端使用的备用地址，必须是 HTTPS 且响应结构兼容 |

定位缓存为 24 小时。主服务失败后尝试备用；备用也不可用时返回限期旧缓存；没有可信数据则返回 503。供应商失败冷却 60 秒，再尝试恢复。

原备用接口是否接受指定访客 IP 尚未得到文档确认，因此返回城市必须与高德定位结果或指定城市编码匹配。没有可信目标城市时不会拿服务器所在地充当访客城市。旧接口只有最高、最低温度时，前端显示中间值并标注“约”，不当作实时温度。

目前备用站点探测出现证书错误，在线文档也未能访问；已按仓库原接口结构封装并用模拟响应验证，不能保证其在线可用，也不会关闭 TLS 校验。显式指定 `city` 时，如果备用响应没有对应行政区划编码，会拒绝使用。

月计数保存在 `weather-data` 命名卷的 `/data/amap-usage.json`，按北京时间自然月重置，容器重建不丢计数。删除数据卷会丢失计数；不要执行 `docker compose down -v`。默认仅支持单实例，不要用多个天气容器共享该计数文件。

4000 是本服务的保守请求上限，不是对高德当前免费额度的声明，也不控制同一 Key 在其他应用产生的请求或账单。按自己的控制台额度调整；额度耗尽后，已有可信城市可继续尝试备用或旧缓存，新访客可能因无法定位而暂不可用。

## 5. 验证与回滚

```bash
cd /home/alvis/nest-home
docker compose --env-file .deploy.env ps
curl -f http://127.0.0.1:8000/api/weather/health
# 明确指定城市验证完整上游调用，会计入请求次数。
curl -f 'http://127.0.0.1:8000/api/weather?city=110101'
docker compose --env-file .deploy.env logs --tail 50 weather
```

再从浏览器访问正式域名，检查 `/api/weather` 的返回城市。该请求不应携带 Key，浏览器也不应请求高德或原备用接口。直接从服务器访问本机地址且不指定城市，没有真实访客 IP，返回不可用是预期行为。

服务日志和错误响应不会输出上游带 Key 的 URL 或原始异常。503 时优先检查 Key 类型、服务器出口白名单、请求上限、上游连通性和可信代理设置；`/api/weather/health` 仅用于判断进程及转发链路存活。

回滚时将 `.deploy.env` 的 `IMAGE` 和 `WEATHER_IMAGE` 一起改为上一个成功提交的镜像标签，然后执行以下命令。若仓库镜像私有，手动操作前需要有拉取权限的 GHCR 登录，CI 临时登录不会保留到日常终端。

```bash
docker compose --env-file .deploy.env pull app weather
docker compose --env-file .deploy.env up -d --no-build --wait app weather
```

首次引入天气服务之前的旧版本还需要匹配当时的 Compose。回滚保留 `.env.weather` 和 `weather-data` 卷。

## 6. 独立部署与本地开发

单独使用天气镜像时，在 `services/weather` 目录复制 `.env.example` 为 `.env`、填入 Key，执行 `docker compose up -d --build --wait`。该 Compose 发布 `127.0.0.1:8001 → 3001`，其他站点可通过宿主机 Nginx 转发 `/api/weather` 到 8001，并设置 `X-Real-IP`。不要同时以为主 Compose 和独立 Compose 使用的是同一实例；它们有独立的计数和缓存。

本地不需要 Docker：使用 Node 22，在 `services/weather/.env` 填写 Key，设置 `DATA_DIR=./data`、`TRUST_PROXY=false`，在仓库根目录执行：

```powershell
pnpm --dir services/weather start
```

另一个终端启动 `pnpm dev`。前端 `.env` 使用 `VITE_WEATHER_API="/api/weather?city=110101"`，Vite 自动代理到本机 3001。正式构建模板默认 `/api/weather`，按真实访客定位；不要把本地固定城市配置提交到生产模板。

测试命令：`pnpm --dir services/weather test`。测试使用模拟上游和临时计数目录，不请求真实天气、不消耗额度。
